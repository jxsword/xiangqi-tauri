# 安装与运行问题排查记录

> 记录本项目的两个实际排障案例：deb 安装失败（包名非法）与 WSLg 环境白屏。
> 适用于后续开发与部署时快速定位同类问题。
> 记录环境：构建机 Ubuntu 22.04（deb 产物来源）/ 运行机 WSL Ubuntu 26.04（WSLg）。

---

## 一、deb 安装失败：无效的软件包名（Package 字段）

### 1.1 现象

使用 `gdebi` 或 `apt install` 安装 `中国象棋_0.1.0_amd64.deb` 均报错：

```
dpkg: 处理归档 中国象棋_0.1.0_amd64.deb (--install)时出错：
 在解析文件 '/var/lib/dpkg/tmp.ci/control' 第 1 行附近时：
 无效的软件包名存在于 'Package' 字段: 必须以字母或数字开头
在处理时有错误发生：
 中国象棋_0.1.0_amd64.deb
```

`apt install` 还会出现“注意，选中 '中国象棋' 而非 './中国象棋_0.1.0_amd64.deb'”的提示。

### 1.2 原因分析

1. **根因**：deb 的 control 文件 `Package` 字段直接取自 Tauri 的 `productName`（本项目中为中文“中国象棋”）。
2. **dpkg 命名规范**：Debian 策略要求 `Package` 字段必须由小写 ASCII 字母、数字以及 `+ - .` 组成，且**必须以字母或数字开头**。中文“中”不是合法首字符，dpkg 在解析 control 阶段即拒绝。
3. **Tauri bundler 限制**：Tauri 的 deb 打包没有独立的“包名”配置项，`Package` 字段固定取 `productName`（转小写）。因此中文产品名必然产生非法包名，属于 Tauri 对非 ASCII 产品名的已知缺口。

### 1.3 解决方案

分两层修复：

**① 源码层：设置合法的二进制名**

在 `src-tauri/tauri.conf.json` 增加：

```json
{
  "productName": "中国象棋",        // 显示名：窗口标题、桌面菜单名
  "mainBinaryName": "xiangqi"       // 二进制名：usr/bin/xiangqi、deb 相关路径
}
```

- `mainBinaryName` 使安装的二进制为 `/usr/bin/xiangqi`（合法 ASCII）；
- 桌面入口 `.desktop` 的 `Exec` 自动指向 `xiangqi`；
- 显示名仍为“中国象棋”，不影响用户观感。

**② 产物层：构建后重打包修正 Package 字段**

由于 bundler 仍以 productName 作为 `Package` 字段（实测即使设置 `mainBinaryName` 也如此），需要在构建后把 control 中的 `Package` 修正为 `xiangqi`。已自动化进 `build-linux.sh`：

```bash
dpkg-deb -R 原包 /tmp/debfix/extract
sed -i 's/^Package: .*/Package: xiangqi/' /tmp/debfix/extract/DEBIAN/control
dpkg-deb --build /tmp/debfix/extract xiangqi_0.1.0_amd64.deb
```

### 1.4 验证

```bash
# 修正后包元数据（Package 字段必须合法）
dpkg-deb -I xiangqi_0.1.0_amd64.deb | grep -E 'Package|Version|Depends'
# 输出示例：
# Package: xiangqi
# Version: 0.1.0
# Depends: libwebkit2gtk-4.1-0, libgtk-3-0

# 安装
sudo apt install ./xiangqi_0.1.0_amd64.deb
# 装后确认
which xiangqi          # /usr/bin/xiangqi
dpkg -s xiangqi | grep Status
```

### 1.5 结论

- 中文 `productName` 会直接导致 deb 包名非法，必须配合 ASCII 的 `mainBinaryName` 使用；
- deb 的 `Package` 字段需构建后二次修正（Tauri bundler 无此配置项）；
- 旧包 `中国象棋_0.1.0_amd64.deb` 无法安装，属预期，直接使用修正后的 `xiangqi_0.1.0_amd64.deb`。

## 二、WSLg 环境启动白屏

### 2.1 现象

WSL Ubuntu 26.04 中运行 `xiangqi`，窗口弹出但内容白屏，终端输出：

```
libEGL warning: DRI3 error: Could not get DRI3 device
libEGL warning: Ensure your X server supports DRI3 to get accelerated rendering
D3D12: Removing Device.
```

### 2.2 原因分析

1. **渲染链路**：WSLg 为 Linux 应用提供虚拟 GPU，其路径为：
   ```
   WSL 内应用 (WebKit/EGL)
     → mesa d3d12 gallium 驱动（WSLg 虚拟 GPU）
     → /dev/dxg → Windows D3D12 API
     → Windows 当前默认 GPU
   ```
2. **崩溃点**：`D3D12: Removing Device` 表示该虚拟 GPU 链路中的 D3D12 设备被移除（驱动崩溃）。随后 WebKitGTK（本机 2.52.6）的硬件渲染路径挂掉，且未成功回退到软件渲染，导致窗口白屏。
3. **与“独显直连”无关**：独显直连是 Windows/BIOS 层“哪块 GPU 直接输出到屏幕”的配置；WSLg 的虚拟 GPU 走的是独立的 D3D12 桥接，借用 Windows 当前默认 GPU（实测本机为 Intel 核显，独立 GPU 未出现在设备列表）。两者路径独立，配置独显直连不能改变 WSLg 内部渲染栈。
4. **影响范围**：WSLg 虚拟 GPU 环境特有；真实 Linux 桌面（物理 GPU 或正常 llvmpipe 回退）不受影响。

### 2.3 解决方案

强制 WebKit 走纯软件渲染（mesa llvmpipe），完全绕开崩溃的 D3D12 虚拟 GPU 链路：

```bash
# 运行时一次性
LIBGL_ALWAYS_SOFTWARE=1 WEBKIT_DISABLE_DMABUF_RENDERER=1 xiangqi

# 永久生效（写入 shell 配置）
echo 'export WEBKIT_DISABLE_DMABUF_RENDERER=1' >> ~/.bashrc
echo 'export LIBGL_ALWAYS_SOFTWARE=1' >> ~/.bashrc
source ~/.bashrc
```

说明：

- `LIBGL_ALWAYS_SOFTWARE=1`：强制 mesa 软件渲染（llvmpipe），不加载 d3d12 后端；
- `WEBKIT_DISABLE_DMABUF_RENDERER=1`：禁用 WebKitGTK 2.42+ 默认启用的 DMABUF 合成渲染器（WSLg 下已知兼容问题）；
- 性能影响可忽略（下棋类界面），开发模式（`npm run tauri dev`）同样需要这两个变量。

### 2.4 验证

设置环境变量后启动，窗口正常渲染并可交互，终端无 D3D12 报错。
